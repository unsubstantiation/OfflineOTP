# Golden interop blobs

Fixed-vector files that pin the on-disk formats shared by the Android app and the desktop client.
`GoldenInteropTest` hashes every file and opens each blob through the real desktop storage stack,
so a silent change to the codecs, the PBKDF2 split or the byte framing fails the build.

The base encrypted vault/backup blobs below use the password `golden-interop-password` and the same two-entry vault document
(`expected-vault.json`, produced by the shared `VaultJson` encoder): a 6-digit SHA1 TOTP for
`Golden Issuer` and an 8-digit SHA256 HOTP (counter 9) for `Counter Service`.

| File | Format | Fixed parameters |
| --- | --- | --- |
| `argon2id-secrets.dat` | nonce-prefixed AES-256-GCM over the vault JSON | Argon2id v1.3 (`65536` KiB, `t = 3`, `p = 4`, 512-bit output), salt `00..0f`; GCM nonce `10..1b`; key = lower 32 bytes |
| `argon2id-vault.properties` | desktop settings for the Argon2id vault | `auth_kdf=argon2id`, `auth_memory_kib=65536`, `auth_iterations=3`, `auth_parallelism=4`, Base64 URL-safe 32-byte verifier and 16-byte salt |
| `argon2id-otp_accounts.json.aes` | `"OOTP" ‖ 0x01 ‖ BE32(65536) ‖ BE32(3) ‖ 0x04 ‖ 16-byte salt ‖ 12-byte nonce ‖ GCM ct ‖ 16-byte tag` | Argon2id v1.3 (`65536` KiB, `t = 3`, `p = 4`, 256-bit key), salt `40..4f`, nonce `50..5b` |
| `secrets.dat` | legacy nonce-prefixed AES-128-GCM over the vault JSON | PBKDF2 salt `00..0f`, 4096 iterations; GCM nonce `10..1b`; key = lower 16-byte PBKDF2 half |
| `vault.properties` | legacy desktop settings for the PBKDF2 vault | Base64 URL-safe verifier (upper PBKDF2 half) and salt, iteration count 4096 |
| `otp_accounts.json.aes` | legacy `4-byte BE iterations ‖ 12-byte salt ‖ 12-byte nonce ‖ GCM ct ‖ 16-byte tag` | 140000 iterations, salt `20..2b`, nonce `30..3b` |
| `expected-vault.json` | compact `VaultJson` document | plaintext shared by all encrypted blobs |

## Regeneration

The checked-in generator is `scripts/packaging/GoldenFixturesGenerator.kt`, driven by
`scripts/packaging/generate-golden-fixtures.sh`. It compiles against the sandbox-built `:core`
output (`reports/kotlin-sandbox/desktop/core`) and the Kotlin stdlib, calling only
`CryptoPrimitives` and the same byte framing the codecs use, with the fixed salts/nonces above
instead of random bytes. `vault.properties` has its `Properties.store` timestamp comments stripped
so the file is deterministic.

```
scripts/kotlin-sandbox/compile-desktop.sh      # builds the :core output the generator uses
scripts/packaging/generate-golden-fixtures.sh  # fails if regenerated bytes drift from the fixtures
```

The default run verifies byte-identical regeneration and never touches this directory; pass
`--write` to replace the fixtures after an intentional format change, then update the SHA-256 pins
in `GoldenInteropTest.expectedHashes`.

`desktop-export.json.aes` is a separate, nondeterministic sample produced by the actual desktop
`BackupCoordinator.encryptedBackup` from `expected-vault.json` using the same test password. Its
random salt and nonce are pinned rather than regenerated by the fixed-vector generator. The Android
instrumentation test consumes this exact desktop export, along with the current fixed vector. `desktop-note-export.json.aes` is another actual desktop export containing those two OTPs
and a multiline Unicode note titled `Recovery`; it uses the same throwaway password. These Android
tests must still be run on a device or emulator to verify that runtime.
`desktop-ssh-export.json.aes` is an actual desktop export containing both fake SSH key fields
(the private field exceeds 5 KiB) and those same OTPs. All keys in these fixtures are test data.

`desktop-privacy-export.json.aes` is a desktop-produced mixed OTP, note and SSH backup with
both hidden and revealed entries. Android device restore sources cover this case; current platform verification is user-reported.

The Swift package in `ios/` reads these files **in place** as well (`GoldenCorpus` locates this
directory from its own source path), so their source coverage uses the same bytes the JVM suites pin. Those legacy tests
are not executed by the current iOS workflow; fixture consumers alone do not establish
a native pass. They never write here.

These are test-only fixtures with a throwaway password and no real accounts.

## Hardware and session-backup contracts

`automatic-backup-options.json` pins foreground session-backup defaults and validation boundaries,
including UTF-16 password-length units. `AutomaticBackupOptionsContractTest` and Swift's
`AutomaticBackupPolicyTests` consume exactly this file; it is not an encrypted vault fixture.

`hardware-unlock-envelope.json` contains **synthetic** credential IDs, salts, PRF values, keys,
nonces and authenticated envelopes for 16/24/32-byte vault keys and credential-ID bounds. They are
not real hardware credentials. The deterministic independent generator is
`scripts/packaging/generate-hardware-unlock-fixtures.py` (test-only Python `cryptography` dependency).
JVM `HardwareUnlockEnvelopeContractTest` checks exact seal/open bytes and tampering; Swift
`HardwareUnlockEnvelopeTests` uses the same vectors. Added Swift tests still require macOS execution.
These vectors are not native transport verification. The iOS PRF source route now uses the official
successor SDK; its Xcode and physical-key acceptance remain pending (see docs/ios-hardware.md).

## Local credential and entry-extension contracts

`automatic-backup-credentials.json` contains independent synthetic AES-GCM/HMAC ABP01 records for
16/24/32-byte vault keys, consumed by JVM and Swift tests. These local records are not portable
preferences or vault backups. `hardware-oath-copy.json` pins shared JVM/Swift copy-to-key naming and
admission rules, including UTF-8 byte limits, period-prefix ambiguity and HOTP counters.

`entry-extension-fields.json` pins opaque newer-client entry metadata: nested arrays/objects, null,
Unicode and booleans. JVM tests exercise save/reload, typed edits, source/output mutation isolation,
common manual-editor replacement, cleanup and rejection of cyclic/overdeep direct object graphs.
Swift tests consume the same document for typed-edit/save/reload preservation. JVM known fields
still use their validated canonical codec; preserving opaque keys does not prove all known-field
normalization/default semantics match Swift. Swift consumers have not been executed in Linux.

### Portable protocol policy (chunk 3)

`portable-vault-protocol.json` contains synthetic framing/dispatch metadata, including legal upper
bounds which must be parsed without deriving keys. Regenerate with
`python3 scripts/fixtures/generate-vault-protocol.py`; `--check` verifies reproducibility.
The same corpus is consumed by desktop/shared-domain tests, Android instrumentation sources and
Xcode app bridge tests. Existing encrypted vectors remain unchanged. See
`docs/portable-vault-protocol.md` for the contract and unexecuted native validation gates.
